## Integration and data protection

One Next.js App Router/TypeScript application uses Server Components for reads, Server Actions for mutations, and pure domain functions. `lib/tmdb.ts` is server-only: Bearer token from `TMDB_READ_ACCESS_TOKEN`, eight-second request timeout, no-store movie reads, distinct not-found/upstream-failure handling and normalized optional fields. Discovery uses server-side genre/Discover/Search endpoints, validated URL state, UTC Newest cutoff and bounded sequential pagination; Search never combines Discover constraints. TMDB scores are not IMDb scores. Approved M25-SUP-01/02 supersede the earlier first-page-only/no-filters/no-sorts restriction and unconditional Popular browse baseline; the defaults, page cap and two-mode contract are recorded in the spec.

Supabase Auth supplies ordinary user sessions through cookie-aware clients/proxy. Safe local return paths are allowlisted. Mutations derive the actor from verified Auth and validate inputs. New Watchlist saves fetch canonical TMDB metadata server-side; removals use owner-scoped keys, and session creation copies existing saved snapshots. PostgreSQL stores minimal saved snapshots and session/ballot records, not a copied catalog. Watchlist RLS enforces ownership; the owner-executed session RPCs check membership, fixed candidates, immutable ballots and delayed intersection results. Other participants’ raw votes are withheld. No application service-role key is used. Public catalog snapshots contain no personalized data; auth cookie refresh preserves no-cache headers. Isolated rules tests do not prove deployed policy or Auth configuration.
